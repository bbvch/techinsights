## Notes (temp)

### Description Draft

A practical experience report on building a complete home automation system end-to-end with AI assistance, with no prior background in Shelly devices or home automation. The project covers hardware setup with 8x Shelly 2PM Gen3 smart switches, a TypeScript controller deployed to the Shellys via Shelly Forge, and a Python proxy on a Synology DSM that fetches sun radiation data from the MeteoSwiss open data API. Claude Code helped design the architecture, derive the sun position and shading algorithms, generate test cases, and write code snippets. The honest takeaway: AI alone takes too many shortcuts, but when paired with clear guidance, defined patterns, and engineering review, the outcome is genuinely good. Includes what worked, what didn't, and where human judgment made the difference.

- 8 shelly devices running blinds automation logic
  - type script
  - sun calculations (sun position, sun in front of window, window overhang)
  - fetch radiation data from nas via web request (json)
  - blinds logic (bed time, manual override via swtiches, sun requires coverage or not)
  - command mapping (open / close / adjust) to shelly commands
  - logging (status, decision, action)

### Findings

From idea to PoC in two days. MVP in three days total.

- AI wanted to take short cuts all the time (increase cyclomatic complexity of functions, behavior testing instead of input/output testing, introduce heavy dependencies for lightweight issues)
- some fixes introduced new issues
- find limitations of devices (e.g. available RAM) and match to solution variants, bring up new solutions (cannot read open data api directly due to file size increasing later in the day so that not enough ram for parsing -> introduce web proxy -> run simple python parser and expose required data only on NAS)
- analyse data source and propose what data to use to base decision on, then generate simple parser in python
- circular behavior in problem solving (limitations in specific ES version, introduced contradicting test cases)
- find limitations in specific operating systems (dsm 6 vs 7)
- compare solution variants
- find and explain algorithm for geometrical problem
- bring up new solutions to improve signal condition (hysteresis, modulation)
- find missing edge cases in test cases
- fix implementation issues based on test cases
- fix runtime issues based on error output
- feedback to improve code readability/maintainability
